# Migrating from the published pre.2 binary to the pre.3 candidate

Japanese: [v0.1.0-pre.3-migration.ja.md](v0.1.0-pre.3-migration.ja.md)

`v0.1.0-pre.3` is **not published yet**. Run its candidate binary only by
extracting the CI artifact built from an explicitly recorded candidate commit;
do not use a pre.3 download URL. The [pre.2 README installation and tour]
(../../README.md#install) remain instructions for the published pre.2 asset.
The QZT on-disk `qzt-0.1` format and `qzt 0.1.0-pre.3` CLI distribution
version are different version axes. Existing valid QZT v0.1 vectors retain
their bytes and are readable by the candidate.

## Output and Writer changes

CLI file output now rejects an alias of any input, including hard links and
case aliases, and rejects output symlinks. Windows read-only existing outputs
are rejected before writing without changing their bytes, attribute, or DACL.
Writable existing outputs retain the documented access ACL/DACL on replacement;
new output and stdout follow their own contracts. A generic public Writer
rejects a nonempty sink and must be discarded after a streaming error; success
is checked against default Reader limits. A post-replacement durability
diagnostic means replacement happened but durable directory state is not
confirmed. Windows same-volume rename does not prove crash durability of the
directory entry. See [CLI file output](../CLI.md#file-output-safety) and
[Writer API](../API_STABILITY.md#writer-api-consolidation).

## Verification and attestations

The old versionless pre.2 attestation bytes and their signature/timestamp must
be kept **as an inseparable set**. The candidate emits different canonical
`qzt-attestation-v1` bytes, so a new signature and timestamp are required if
you regenerate. A changed attestation is not proof that QZT source bytes
changed. See [canonical form](../CLI.md#attestation-canonical-form) and the
[signing guide](../guides/attestation.md).

`VerifyReport.checked_chunks` is the number of structurally checked Chunk
Table entries, not decoded chunks. `compressed_checksum_chunks` counts checked
compressed payload checksums. `decoded_chunks` and `decoded_bytes` measure
actual decompression. `original_checksum_verified` states whether the entire
source checksum was recomputed. Quick, Normal, and Deep levels therefore have
different evidence; request Deep before claiming restored-source integrity.
Optional index statuses are separate. Complete Rust `VerifyReport` literals
must add the new fields. See [CLI verify](../CLI.md#qzt-verify-file---level-quicknormaldeep---format-textjson)
and [API notes](../API_STABILITY.md).

## Search and limits

Each returned hit is checked against original bytes, but
`index_complete_declared=true` only repeats the index declaration.
`index_coverage_verified=false` means a zero-hit result does not prove the
index contains every source match. `capped=false` and a null `stop_reason`
describe ordinary completion of the inspected candidate set. A named
`stop_reason` with `capped=true` is a verified partial result. A query,
posting, or line hard-limit error exits 1 and is not a successful partial
report. Read the [search CLI](../CLI.md#qzt-search-file-query-options) and
[search operations guide](../guides/search-operations.md) before using a
zero-hit result as absence evidence.

Default `max_search_results` is now 10,000; query, posting, candidate,
physical/logical decode, DLI allocation, and index-build line budgets can
also stop or reject calls formerly accepted by pre.2. Increase only the
specific limit that the workload needs after reviewing its memory/CPU cost.
Rust callers using complete `ResourceLimits`, `SearchOptions`,
`SearchReport`, `SearchMetrics`, `TokenIndexBuildOptions`,
`NgramIndexBuildOptions`, or `VerifyReport` literals must add the new fields;
struct update syntax with `Default` avoids tying callers to every default.
See [API stability](../API_STABILITY.md) for the exact fields and meanings.

## Candidate execution and later publication

For a candidate archive downloaded from the 14-day CI artifact, record its
workflow run, source SHA, archive checksum, extracted binary checksum, and
the platform. Extract it to a fresh directory and run that exact binary path;
the [candidate verifier](../../scripts/verify-release-candidate.py) does this
on each native runner. It does not use an installed `qzt` on `PATH`.

After separate owner approval, use the exact reviewed merge SHA and the
[protected release runbook](../RELEASE.md#pre3-candidate-publication-after-owner-approval).
The release workflow rebuilds assets; compare checksums, version, and extracted
binary smoke on the **published assets** too. Only after publication should
the README installation instructions switch from pre.2 to pre.3.
