## Why pre.5 follows pre.4

The [pre.4 candidate](v0.1.0-pre.4-candidate.md) passed unpublished validation
at source `4715196614c54c54b7809f99a422343ef2cf7b85`. Its annotated tag
remains at that SHA. The tag-only [release run 36257908117 attempt 1](https://github.com/albert-einshutoin/qzt/actions/runs/36257908117)
successfully built all four native artifacts but then rejected an untracked
root `dist-manifest.json` during build-environment verification. Global build
and protected hosting were skipped, so **no pre.4 Release was published**.
The failed run and tag remain historical evidence; #320 was closed as not
planned rather than as a completed publication.

Pre.5 retains the #27 increasing-vector n-gram posting construction and #316
CompactV2 file-backed QZI open improvement. Since pre.4, the product delta is
the CLI distribution-version update plus the native/global tag-only release
workflow repair and supporting validation/documentation. QZT stays `qzt-0.1`;
QZI v1/v2, public API, search fields, and `qzt-attestation-v1` are unchanged.
Review the actual pre.4-to-pre.5 Git diff before publication.

The [#27](../benchmarks/2026-09-issue27-ngram-build.md) and
[#316](../benchmarks/2026-09-issue316-token-open.md) performance results came
from development binaries on fixed synthetic inputs on one Apple M4/macOS
host with uncontrolled OS cache. They are **not pre.5 candidate performance
measurements** or results for published binaries, Linux/Windows, real logs,
concurrent search, fixed RSS limits, or a production SLA.

## Release-path rehearsal and candidate evidence

The generated [tag-only release workflow](../../.github/workflows/release.yml)
keeps the clean source check and writes native/global raw manifests under
ignored `target/release-workflow/`. Both it and the read-only
[candidate workflow](../../.github/workflows/release-candidate.yml) use the same
[build/manifest script](../../scripts/release-workflow-build.sh). The candidate
workflow records each native and global build environment, executes the real
`dist build`, verifies the environment afterward, reads/copies the manifest,
uploads/downloads artifacts, passes all four native outputs into global
checksum/installer construction, and stages the files left after the host's
internal-JSON cleanup. It does **not** call hosting APIs, enter the protected
`release` environment, create a tag or Release, or install from a public URL.

For each of macOS ARM64, macOS Intel, Linux x64, and Windows x64, the native
check records archive/sidecar/extracted-binary hashes, version, linkage where
applicable, and the fixed smoke. The global check verifies source archive
bytes and executable bits against the selected Git tree, all five aggregate
checksums, installer version URLs, and the planned asset set. The
[small compatibility fixture](../../scripts/verify-pre4-compatibility.py)
compares published pre.3 and a selected pre.5 binary for QZT/QZI read/search,
Deep verify/export, and canonical attestation bytes. Candidate artifacts are
ephemeral; use the API `expires_at` recorded in #321 rather than assuming a
retention period from previous runs.

Publication remains a separate decision. It must use a new annotated pre.5
tag on the exact accepted candidate SHA and the protected tag-only workflow.
