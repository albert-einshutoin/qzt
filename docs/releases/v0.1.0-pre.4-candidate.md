# v0.1.0-pre.4 candidate notes (unpublished)

Japanese: [v0.1.0-pre.4-candidate.ja.md](v0.1.0-pre.4-candidate.ja.md)

This is an **unpublished candidate**, tracked by [#318](https://github.com/albert-einshutoin/qzt/issues/318).
The published `v0.1.0-pre.3` binaries came from
`017d4d19739800773ab6a54adf636ff5a43ec1fc`; this candidate starts from
main `f5a38d49447edd6ef95b7610bce3ae2d3be612bc`. The exact candidate
source SHA, native archive hashes, and final run belong to #318 after its PR
is merged. The CLI distribution version becomes `qzt 0.1.0-pre.4`; QZT remains
the `qzt-0.1` container format and QZI retains its existing v1/v2 encodings.
The current [Install](../../README.md#install) and README tour still target the
**published pre.3** assets. No pre.4 tag, Release, crates.io upload, or public
installer download is part of this preparation.

## Changes since published pre.3

- [#27 / PR #315](https://github.com/albert-einshutoin/qzt/pull/315) replaced
  each n-gram key's posting tree set with an increasing vector. Repeated keys
  still produce one posting per granule, with identical tested QZI bytes.
- [#316 / PR #317](https://github.com/albert-einshutoin/qzt/pull/317) removed
  redundant derived CompactV2 term-key hash comparisons from file-backed QZI
  open. LegacyV1 still checks its stored hash before retaining a bad term or
  decoding later records. Full section checksums, source binding, dictionary
  and resource checks, and lazy query reads remain in place.
- The pre.3 publication/README changes since its product commit were
  documentation and read-only public-asset verification. This candidate adds
  explicit version binding to the shared candidate/published verifier and
  records the Rust/Cargo environment immediately around each dist build.

The [#27 n-gram report](../benchmarks/2026-09-issue27-ngram-build.md) and
[#316 token-open report](../benchmarks/2026-09-issue316-token-open.md) measure
development binaries on fixed synthetic inputs on one Apple M4/macOS host.
OS cache was not controlled. The measured improvements have not been
remeasured on candidate/published binaries, Linux/Windows, real logs, or
concurrent search. They imply neither a fixed RSS limit nor a production SLA.

## Compatibility and attestation

The product diff from the pre.3 product commit changes n-gram posting
construction and CompactV2 hash work, but not QZT/QZI encodings, public API,
search result or stop-reason fields, or `qzt-attestation-v1`. A local
[cross-version check](../../scripts/verify-pre4-compatibility.py) used the
published pre.3 macOS ARM binary (archive SHA-256
`0e51e0a1945b984500ae27a21e56930ba4b06a744a639feffa696307b1255b20`)
and a pre.4 development release-profile binary (SHA-256
`12e02b21c28368df07536aa4a6356f5d1e1f1a9c97638a4f30d83c9ef9765158`).
Both binaries Deep-verified and byte-exact exported QZT files made by either
version. On the same QZT at the same Deep level, their canonical attestation
bytes matched exactly (SHA-256
`aadfd74b2052c257e6aca0a7a95654f95a010e40ede760f1bb1c650405a883c3`).
On the fixed repeated-key LF/CRLF fixture, pre.3 and local pre.4 created
byte-identical token and n-gram QZI files; both searched both versions' QZI
and returned the same verified source offsets. The
[local result](raw/v0.1.0-pre.4/compatibility-local.json) records every hash.
This check does not substitute for a final candidate archive check. Because
canonical attestation signing bytes did not change for the same QZT/level,
the CLI version bump alone does not require regenerating an existing
signature or timestamp over those bytes. External envelopes that include a
binary version or other metadata must be assessed separately.

Recheck with the final native macOS ARM candidate binary after download:

```sh
python3 scripts/verify-pre4-compatibility.py \
  --pre3-bin /path/to/verified-pre3/qzt \
  --candidate-bin /path/to/verified-pre4/qzt \
  --output /path/to/compatibility-final.json
```

## Build and publication boundary

The read-only [candidate workflow](../../.github/workflows/release-candidate.yml)
requires an absent pre.4 tag and an exact source SHA in main history for final
dispatch. It builds four native archives, SHA-256 sidecars, installers and a
source archive without hosting. Build environment JSON is captured immediately
before `dist build`, with `RUSTUP_TOOLCHAIN` pinned for the build step, then
checked afterward. It records checked-out SHA, selected Rust/Cargo, target,
cargo-dist 0.31.0, dist profile/default features, relevant flags and runner.
Archive, sidecar and extracted-binary hashes plus native smoke are separate
evidence. The same recorder is in the generated tag-only release workflow so
a later release can capture its actual build environment rather than borrowing
the verifier runner's rustc version. This does not prove bit-for-bit
reproducible builds or equality with a later published asset.

The final candidate's CI artifacts expire after 14 days. If they expire before
publication, rerun candidate verification against the same full source SHA
while pre.4 remains untagged. After publication, use the separate read-only
published-asset verifier against actual Release URLs; an unpublished installer
URL cannot be tested here. Pre.3 candidate, migration, performance and public
asset records remain historical evidence, not pre.4 artifact results.
