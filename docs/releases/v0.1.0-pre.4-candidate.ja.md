# v0.1.0-pre.4候補ノート（未公開）

English: [v0.1.0-pre.4-candidate.md](v0.1.0-pre.4-candidate.md)

これは[#318](https://github.com/albert-einshutoin/qzt/issues/318)で扱う**未公開候補**です。
公開済み`v0.1.0-pre.3`の製品commitは
`017d4d19739800773ab6a54adf636ff5a43ec1fc`、今回の開始mainは
`f5a38d49447edd6ef95b7610bce3ae2d3be612bc`です。最終候補のsource SHA、
native archiveのhashと検証runはPR merge後に#318へ記録します。CLI配布版は
`qzt 0.1.0-pre.4`ですが、QZTは`qzt-0.1`、QZIは既存v1/v2形式のままです。
現在の[Install](../../README.ja.md#install)とREADMEツアーは**公開済みpre.3**へ
案内し続けます。pre.4のtag・Release・crates.io公開・公開URLからのinstaller
導入は今回の準備に含めません。

## 公開pre.3からの変更

- [#27 / PR #315](https://github.com/albert-einshutoin/qzt/pull/315)で
  n-gramのkeyごとのposting tree setを昇順vectorに変更しました。同じgranule
  内の反復keyはpostingを1件とし、確認したQZI byte列は同一です。
- [#316 / PR #317](https://github.com/albert-einshutoin/qzt/pull/317)で
  file-backed QZI openにおけるCompactV2派生term key hashの重複比較を削減
  しました。LegacyV1の保存hashは不正termの保持や次recordのdecodeより前に
  照合します。全section checksum、source binding、辞書・資源検証、query時の
  必要record読込みを維持します。
- pre.3の製品commit後の公開・README変更は文書と読み取り専用の公開物検証
  でした。今回は共有verifierへ期待版を明示し、各dist build直前・直後の
  Rust/Cargo環境を記録・照合します。

[#27のn-gram計測](../benchmarks/2026-09-issue27-ngram-build.md)と
[#316のtoken open計測](../benchmarks/2026-09-issue316-token-open.md)は、
Apple M4/macOSの固定合成入力に対する開発binaryの結果です。OS cacheは
制御していません。候補・公開binary、Linux/Windows、実ログ、並行検索で同じ
改善率を測ったものではなく、固定RSS上限や本番SLAを示しません。

## 互換性とattestation

pre.3製品commitからの製品差分はn-gram posting構築とCompactV2 hash処理で、
QZT/QZIの保存形式、公開API、検索結果・停止理由のfield、
`qzt-attestation-v1`は変更していません。[新旧比較script](../../scripts/verify-pre4-compatibility.py)
で、公開pre.3 macOS ARM binary（archive SHA-256
`0e51e0a1945b984500ae27a21e56930ba4b06a744a639feffa696307b1255b20`）と
pre.4開発release-profile binary（SHA-256
`12e02b21c28368df07536aa4a6356f5d1e1f1a9c97638a4f30d83c9ef9765158`）
を比較しました。新旧が作ったQZTを双方でDeep verify・byte完全一致のexport
ができ、同じQZT・同じDeep levelのcanonical attestationはbyte一致しました
（SHA-256 `aadfd74b2052c257e6aca0a7a95654f95a010e40ede760f1bb1c650405a883c3`）。
LF/CRLFと反復keyの小fixtureでは新旧のtoken／n-gram QZI byte列も一致し、
双方の検索hitは原文と一致しました。[ローカル記録](raw/v0.1.0-pre.4/compatibility-local.json)
にhashを保存しています。最終候補archiveの確認は別に行います。同一QZT・
同一levelの署名対象byteは変わらなかったため、CLI版だけを理由に既存の
署名・timestampを作り直す必要はありません。binary版などを外側の署名対象
に含む場合は別途確認が必要です。

最終macOS ARM候補binaryを取得したら、次のコマンドで比較を再実行します。

```sh
python3 scripts/verify-pre4-compatibility.py \
  --pre3-bin /path/to/verified-pre3/qzt \
  --candidate-bin /path/to/verified-pre4/qzt \
  --output /path/to/compatibility-final.json
```

## ビルド証拠と公開境界

読み取り権限のみの[候補workflow](../../.github/workflows/release-candidate.yml)は
pre.4 tagが存在しないことを検査し、最終dispatchではmain履歴中の完全な
source SHAを要求します。4native archive・SHA-256 sidecar・installer・
source archiveを公開せずに作ります。`dist build`直前のcheckout SHA、選択した
Rust/Cargo、target、cargo-dist 0.31.0、dist profile/default features、関連
flag、runnerを記録し、`RUSTUP_TOOLCHAIN`を固定したbuild後に再照合します。
archive・sidecar・展開binaryのhashとnative smokeは別の証拠です。tag-onlyの
生成release workflowにも同じ記録を追加し、後日の公開物について検証runnerの
rustcをビルド版として代用しません。この記録だけではbit単位の再現ビルドや、
候補と後日の公開物のhash一致を証明しません。

候補artifactの保存期限は14日です。公開前に期限切れになった場合は、pre.4
が未tagの間に同じ完全source SHAで候補検証を再実行します。公開後は実Release
URLを対象とする別の読み取り専用verifierを使います。未公開installer URLの
実downloadは今回確認できません。pre.3の候補・移行・性能・公開物記録は履歴
として残し、pre.4の成果物証拠と混同しません。
